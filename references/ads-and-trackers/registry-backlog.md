# Registry Backlog — SDKs Detected but Not (Fully) Neutralized

The privacy audit (`find-trackers` / `find-ads`) and the neutralizer read the same SDK registry (`registry/*.json`), but the audit knows more than the neutralizer can act on: SDKs with no entry at all, *detection-only* entries (no `targets`), and `detection` facts (packages, APIs, manifest names) that are not yet part of the neutralization data. This page lists those gaps so they can be closed later, one reviewed commit per item (each promotion changes what `registry-scan.py` emits and must come with a reviewed golden diff).

Gap types:

| Type | Meaning |
|---|---|
| **E** | no registry entry |
| **DO** | detection-only entry: the audit reports it, `registry-scan.py` skips it, nothing is stubbed |
| **P** | a package the audit attributes to the SDK that is not in its `packages` (neutralizer identity) |
| **A** | an API the audit recognizes that is not a neutralization target |
| **M** | a manifest component that is not in `manifest_components` |

How to close a gap: add `targets` / `manifest_components` / `packages` to the **existing** entry (never a second entry for the same SDK), run the registry lint and the golden tests (`tests/run.sh quick`, `tests/run.sh golden` in the repo), and refresh the generated table below (`bash tests/tools/registry-gaps.sh --write`). Suggested order for the promotions of known `detection` facts: InMobi manifest components and Pangle `com.pgl.ssdk` first, then Appodeal (`com.explorestack` is BidMachine's) and Facebook (`com.facebook.ads` is Meta Audience Network's).
